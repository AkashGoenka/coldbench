# Example corpora

Two question sets generated by the method in [`skills/build-prompts/SKILL.md`](../skills/build-prompts/SKILL.md),
with the ground truth they were scored against. They are here so you can see what a finished
corpus looks like before building your own, and so `score.mjs` has something real to run on.

| Corpus | Repo | Language | Questions | Gold files |
|---|---|---|---|---|
| `arches/` | [archesproject/arches](https://github.com/archesproject/arches) | Python / Django | 32 | 123 |
| `jmri/` | [JMRI/JMRI](https://github.com/JMRI/JMRI) | Java | 25 | 93 |

Both are public repositories, and every question derives from a closed public issue. The
question text is a rewrite of the reporter's own description; the gold file set is the file
list of the commit that closed the issue.

## Layout

```
arches/
  prompts/arches_q01.txt ... arches_q32.txt   one question per file, contract appended
  ground_truth.json                           qid -> { issue_number, scope, files }
```

Each prompt is paired 1:1 with a gold entry — no question lacks ground truth and no gold
entry lacks a question.

## The gold format

```json
"arches_q01": {
  "issue_number": 12689,
  "scope": "single",
  "files": [
    "arches/app/templates/base-manager.htm",
    "arches/app/templates/navbar/sidenav.htm"
  ]
}
```

`files` is what `score.mjs` reads. `issue_number` lets you check any question against the
original issue. `scope` is the stratification axis, and it is worth reporting separately
rather than only in aggregate:

| scope | arches | jmri | meaning |
|---|---|---|---|
| `single` | 11 | 8 | the change landed in one area |
| `multi-file` | 13 | 12 | several files, one subsystem |
| `cross-cutting` | 8 | 5 | spans subsystems |

A tool that helps on `single` and not on `cross-cutting` is a different claim from one that
helps on average, and the average hides it.

## Running one

The prompts are ready to paste. Each ends with the output contract, so a run leaves answer
files behind in `./benchmark_output/`:

```
node scripts/score.mjs \
  --gold examples/arches/ground_truth.json \
  --arm base:~/bench/arches-base/benchmark_output:~/bench/arches-base \
  --arm tool:~/bench/arches-tool/benchmark_output:~/bench/arches-tool
```

Check the arms with `inspect.mjs` first; see the main README.

## Caveats worth knowing before you quote these

**Gold comes from the closing commit, so it includes files that are not really the answer** —
a lint fix or a changelog touched in the same commit counts as gold. This costs precision
more than recall, and it costs both arms equally, which is why precision here sits near 40%
while recall sits near 76%. Read precision as a relative number between arms, not an
absolute.

**The question text keeps the reporter's vocabulary**, including feature and symbol names.
That is deliberate: real developers use codebase vocabulary when they prompt. On arches, 7 of
32 questions spell out a multi-word gold filename, and 5 of those are migrations, whose
filenames are English descriptions of the change. Measure and report that split; do not strip
it.

**`arches_q28` through `arches_q32` have gold but were not used** in the published runs, which
covered q01–q27. They are included because they were generated by the same pass.

**These are a starting point, not a benchmark suite.** Both repos are well-known and public,
so a model may recall parts of them from pretraining. For a result you intend to publish,
generate a corpus from a repo the model is less likely to have memorised — ideally your own.
The `unseen` count in `score.mjs` is the check for this.
